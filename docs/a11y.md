# Accessibility audit

Audit of the M6 polish milestone, run on 2026-09-19 against commit `36be0ae`. The app ran in a browser on the mock backend, with axe-core 4.x and keyboard-only passes. It was checked at 1440×900, with a spot-check at 1100×700, in English and in Italian. The fixes below were then applied and checked again the same way: axe on every screen that changed, the keyboard flows, and 1100×700 in Italian. This file holds the results, the contrast tables and the steps to run the audit again.

## Summary (after the fixes)

- **axe (WCAG 2.x A/AA rules):** no violations on these screens:
  - Explore: grid, filters, vehicle suggestions, Following.
  - Skin detail: loading, loaded, and after Back.
  - My Hangar: grid, list, bulk bar.
  - Collections.
  - Install queue, including the "Pick vehicle" menu.
  - Settings, with the Licenses dialog.
  - The command palette.
  - First run.
  - The same screens in Italian at 1100×700.
- **One report is expected and harmless.** axe may flag the 8px `ink-5` file labels on First run's atlas tiles (`[data-tile]`) once they have animated in. The drawing is `aria-hidden` decoration, so WCAG 1.4.3 does not apply. Exclude the tiles in automated runs (see "How to re-run the audit").
- **axe does not measure everything.** It skips text over the `bg-grid` / `bg-placeholder*` gradients and hover-only colours. Those pairs were checked by hand against the tables below.
- **Keyboard:**
  - Every control can be reached and has a visible 2px amber ring.
  - Dialogs (conflict, licenses, palette) trap focus. Escape closes only the top layer.
  - Focus returns to the opener after a menu, dialog or palette closes.
  - Opening a Skin detail puts focus on its `<h1>`. That is the skin name, or "Skin detail" while the post loads or can't be loaded.
  - Back from a Skin detail puts focus on the card that opened it. In Explore's virtual grid the card is scrolled into view first. When the card isn't on the screen, focus goes to the screen's `<h1>`.
  - Section shortcuts (1–5 and `,`) put focus on the new screen's `<h1>`, so the screen is announced. So do palette results that open another screen or skin.
  - Any other screen change that takes the focused control away puts focus on the new screen's `<h1>` too, for example "Open My Hangar" in an offline state, or the end of First run.
  - In My Hangar, F6 jumps from the list or the toolbar to the bulk bar, and back.
  - Ctrl+K doesn't open the palette over another modal dialog.

## Fixes applied (M6 polish)

### Medium findings

- **Focus is lost when the Skin detail opens.**
  - Every variant of the top bar has an `<h1 tabIndex=-1>`: loading, loaded, offline or error, and no skin. It holds the skin name, or an `sr-only` "Skin detail".
  - When the detail mounts or the skin changes, and focus has fallen to `<body>`, the heading takes focus.
  - Files: `Detail/DetailTopBar.tsx`, `Detail/SkinDetail.tsx`.
- **Back from the detail drops focus.**
  - `ui.leaveDetail()` goes back to `detailReturnTo` and sets `returnFocusSkin`.
  - Explore's `SkinGrid` claims the skin when it is in the loaded pages. It keeps the card's line mounted, scrolls to it (`scrollToIndex`, centred) and focuses the card.
  - Otherwise `useScreenFocus` focuses the rendered card: in Explore and Following by `data-skin-id`, in My Hangar by the new `data-source-id`. If no card is rendered, it focuses the screen's `<h1>`.
  - Files: `store/ui.ts`, `hooks/useScreenFocus.ts`, `Explore/SkinGrid.tsx`, `Hangar/SkinCard.tsx`, `Hangar/SkinRow.tsx`.
- **Explore has no `<h1>`.**
  - An `sr-only` `<h1>` "Explore" now opens the screen.
  - Each card's name is an `<h2>`, with the same styling as before.
  - Files: `Explore.tsx`, `Explore/SkinCard.tsx`.
- **The `ink-4` code on a highlighted option is 4.24:1.**
  - The vehicle combobox shows the code in `ink-3` on the highlighted option (5.94:1).
  - Menu items are now a Tailwind `group`, so the "Pick vehicle" code turns `ink-3` with the item's `hover` / `focus-visible` background.
  - Files: `Explore/VehicleInput.tsx`, `ui/Menu.tsx`, `Queue/QueueRow.tsx`.
- **The palette's kind column and footer use `ink-5`.**
  - The kind column and the hints are `ink-4` (4.59:1 on bg-3), and `ink-3` on the highlighted row (6.14:1 on bg-hover).
  - The footer hints and the Esc key cap are `ink-4`, through a new `Kbd` tone `ink4`.
  - `ink-5` stays only on the sidebar key hints, which are `aria-hidden`.
  - Files: `chrome/CommandPalette.tsx`, `ui/Kbd.tsx`.
- **First run's future steps use `ink-5` (3.57:1).**
  - They are `ink-4` now (4.81:1 on bg-2). The Explore card's upcoming install steps made the same call.
  - The `·` separators stay `ink-5`, because they are decoration.
  - **This deviates from the README.** The author can revert it (see "Open decisions for the author").
  - File: `FirstRun/StepTracker.tsx`.

### Low findings

- **The size on a hovered Hangar list row is 4.39:1.** The row is a `group`, and the size turns `ink-3` on hover, as it already did on selected rows. File: `Hangar/SkinRow.tsx`.
- **The detail's placeholder labels are 4.2–4.49:1 on the stage stripes.** They are `ink-3` now, about 5.9:1 on the lighter stripe. Files: `Detail/Gallery.tsx`, `Detail/Compare.tsx`.
- **A truncated attention message has no tooltip.** The full-card or full-row hit area lies over the text, so the hit area's own `title` now holds the name and the message on two lines. File: `Hangar/SkinParts.tsx` (`useSkinDescription`).
- **Screen readers miss the attention message, and the Active toggle reads "Inactive, not pressed".**
  - The hit area's `aria-describedby` lists the key hint and the attention message.
  - The toggle is a `role=switch` with `aria-checked` and a stable name: "Active in game" ("Attiva in gioco"). The visible text still follows the state.
  - Files: `Hangar/SkinParts.tsx`, `Hangar/SkinCard.tsx`, `Hangar/SkinRow.tsx`.
- **Section shortcuts leave focus on `<body>`.**
  - A section key that changes the screen calls `ui.focusHeading()`. `useScreenFocus` is mounted with the shortcuts in App, and it focuses the new screen's `<h1>` after the screen renders.
  - The palette does the same when its result opens another screen or skin, instead of returning focus to its opener. When the opener is gone, it falls back to the heading.
  - Any other screen change that leaves focus on `<body>` (the focused button went away with the old screen) also lands on the new screen's `<h1>`. Focus that survives the change, such as a sidebar button, is left alone.
  - Every screen `<h1>` is `tabIndex=-1` with no ring, as in First run.
  - Files: `hooks/useKeyboardShortcuts.ts`, `hooks/useScreenFocus.ts`, `chrome/CommandPalette.tsx`, `ScreenHeader.tsx`, `Collections.tsx`, `Collections/CollectionList.tsx`, `Settings.tsx`.
- **Ctrl+K opens the palette over a modal dialog.** Ctrl+K is now ignored while another `aria-modal` dialog is open. It still closes an open palette. File: `hooks/useKeyboardShortcuts.ts`.
- **The bulk bar is far from the selected card in Tab order.**
  - F6 moves focus to the bar's first control. From the bar, F6 goes back to the last focused skin, or to "Select all".
  - The toolbar has `aria-keyshortcuts="F6"`, and the selection status adds "Press F6 to reach the actions for the selection."
  - Files: `Hangar.tsx`, `Hangar/BulkBar.tsx`.

## Open decisions for the author

- **First run's future steps.** The README asks for `ink-5`. They now use `ink-4` for AA (4.81:1 instead of 3.57:1). To go back, change `text-ink-4` to `text-ink-5` in `StepTracker.tsx` and in the First run test, and record the exception.
- **The palette footer and the Esc key cap.** DESIGN_NOTES "M1 · Contrast" kept them `ink-5` as supplementary hints. They are `ink-4` now. Going back is a one-word change in `CommandPalette.tsx` (the class, and the `Kbd` tone).
- **Control boundaries (WCAG 1.4.11), not changed.**
  - Input, chip and secondary-button borders are `line-3` on bg-input or bg-2: 1.33:1 and 1.38:1.
  - The selected segment of a segmented control differs from the track only by its fill (bg-5 vs bg-chip, 1.14:1) and its text colour.
  - Placeholders, icons and text identify the controls, so this is borderline. Fixing it moves away from the prototype.
  - Options: an `ink-5` border on focusable inputs (3.44:1 on bg-input), and a 1px `ink-3` or amber inset ring on the selected segment.
- **The Active switch's name vs its visible text (WCAG 2.5.3).**
  - The switch is named "Active in game", while the off state shows "Inactive".
  - Voice-control users say "click Active in game", or use numbers.
  - The alternative is a name that follows the visible text, and that is what the audit flagged as contradictory for screen readers.

## How to re-run the audit

Do not audit `pnpm dev:mock` while other work is being saved. Every save triggers a Vite full reload, which drops the injected axe and the focus log. Audit a frozen build instead.

1. **Build a frozen mock bundle** (from the repo root, Git Bash):

   ```bash
   S=/tmp/livery-a11y            # or any scratch folder
   mkdir -p "$S/snap"
   git archive HEAD | tar -x -C "$S/snap"
   cmd //c mklink //J "$(cygpath -w "$S/snap/node_modules")" "$(cygpath -w "$PWD/node_modules")"
   (cd "$S/snap" && ./node_modules/.bin/vite build --mode mock --outDir "$S/dist" --emptyOutDir)
   cp node_modules/axe-core/axe.min.js "$S/dist/"
   (cd "$S/snap" && ./node_modules/.bin/vite preview --outDir "$S/dist" --port 1441 --strictPort)
   ```

   When you are done, remove the junction with `cmd //c rmdir <snap>\node_modules`. `rmdir` on a junction does not touch the real `node_modules`.

   If nobody else is editing files, `pnpm exec vite --mode mock --port 1441 --strictPort` works too. In that case load axe from `/node_modules/axe-core/axe.min.js`.

2. **Open the states:**
   - `http://localhost:1441/`: First run (found, then import)
   - `?notfound=1`: First run, not found
   - `?onboarded=1`: the full app
   - `&offline=1`: WT Live offline
   - `&empty=1`: empty Hangar and Collections
   - `&many=1`: 1,000 skins and 1,284 posts
   - Explore with no results: type an unknown code in the Vehicle box and press Enter.
   - Drop overlay and error row: run this in the page:
     ```js
     const dt = new DataTransfer();
     dt.items.add(new File(['x'], 'a.zip'));
     window.dispatchEvent(new DragEvent('dragenter', { dataTransfer: dt }));
     ```
     Then dispatch a `drop` event the same way.
   - Italian: Settings → Language → Italiano.
   - Sizes: 1440×900, and 1100×700 for the minimum window.

3. **Run axe** in the DevTools console on each state:

   ```js
   if (!window.axe) (0, eval)(await (await fetch('/axe.min.js')).text());
   (await axe.run(document, { resultTypes: ['violations'] })).violations
     .map(v => [v.id, v.nodes.map(n => n.target.join(' ') + ' :: ' + n.any[0]?.message)]);
   ```

   Open menus, dialogs, the palette and toasts before you run it, so their content is checked. Hover-only colours (for example `ink-4` on a hovered row) and text over `bg-grid` / `bg-placeholder*` gradients are not measured by axe. Check them against the table above. On First run, skip the decorative atlas labels: `axe.run({ include: [document], exclude: [['[data-tile]']] }, { resultTypes: ['violations'] })`.

4. **Keyboard pass.** Log focus while you press Tab:

   ```js
   document.addEventListener('focusin', e => console.log(e.target.tagName, e.target.getAttribute('role'),
     e.target.getAttribute('aria-label') || e.target.innerText.slice(0, 40)), true);
   ```

   Check on every screen:
   - Tab order is logical and every control shows the amber ring.
   - Tab never gets stuck outside a modal.
   - Escape closes only the top layer.
   - Focus goes back to the opener after a menu, dialog or palette closes, and to the skin's card after returning from Skin detail.

   Automation note: CDP-synthesised Enter/Space do not activate native `<button>`s in the embedded browser pane. Use real keys, or `.click()` for native buttons, and synthetic `keydown` for custom `role=button` widgets.

   Also check that focus lands on the screen's `<h1>` after a section shortcut or a palette result, on the skin's `<h1>` when a Skin detail opens, on the card after Back, and that F6 jumps to My Hangar's bulk bar and back.

   Second automation note: when the browser window doesn't have system focus (`document.hasFocus()` is false, e.g. the pane is hidden), `element.focus()` moves `document.activeElement` but fires no `focus` / `focusin` events, so React's `onFocus` handlers don't run. Checks that depend on them (My Hangar's "last focused skin" for F6 and bulk actions, the virtual grids' focused line) need the window focused, or a synthetic `focusin` after `focus()`.

5. **Recompute contrast** when a token changes. Resolve the colour through a 1×1 canvas: `fillStyle = token`, then `getImageData` gives sRGB. OKLCH tokens and alpha tokens are composited over their real surface this way. Then apply the WCAG relative-luminance formula and update the tables above.
